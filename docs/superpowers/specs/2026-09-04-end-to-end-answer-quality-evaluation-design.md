# End-to-End RAG Answer Quality Evaluation Design

## Context

Issue #130 asks for an offline, deterministic evaluation layer that measures the
final answer produced by the existing NexusMind query pipeline. Retrieval and
citation validation already expose canonical evidence and replay diagnostics,
but there is no authored way to measure factual coverage, citation support,
groundedness, or correct refusal when evidence is insufficient.

## Goals

- Evaluate complete `KnowledgeBase.query()` runs, including the validated final
  answer and its canonical citations.
- Keep evaluation policy outside production retrieval, context assembly, answer
  generation, and citation validation.
- Make authored expectations readable in JSON and reports reproducible without
  network access or a hosted model.
- Compare pipeline configurations, initially `expand_context=True` versus
  `expand_context=False`, on the same corpus and cases.

## Non-goals

- Changing production query defaults or citation contracts.
- Adding an LLM-as-a-judge dependency.
- Inferring arbitrary semantic correctness from free-form text. The deterministic
  baseline uses authored fact phrases and explicit evidence expectations; a
  future optional judge may extend this without changing the baseline contract.
- Web search, new retrieval backends, persistence, or automatic tuning.

## Architecture

Add an `answer_quality_evaluation` module as an external consumer of existing
public query result records:

```text
authored case + local corpus
          |
          v
deterministic fixture query runner
          |
          v
KnowledgeBase.query(...)
          |
          v
KnowledgeQueryResult
          |
          v
pure answer-quality evaluator
          |
          v
per-case result + aggregate stable report
```

The fixture runner creates a temporary local knowledge base, ingests the
authored corpus, and injects an offline `AnswerGenerator`. The generator scans
the supplied context for authored fact markers, emits the corresponding
authored fact text, and cites only the context passages containing those
markers. Cases can also explicitly request an incomplete, unsupported, or
insufficient-evidence behavior so evaluator failure modes are covered without
network or model variability. The evaluator itself accepts query results from
an injected runner, so callers can provide other deterministic configurations.

## Authored case format

Files live under `evals/knowledge/answer_quality/`:

- `corpus/`: small multi-section technical documents;
- `cases.json`: strict JSON authored expectations;
- `baseline.md`: generated byte-stable report.

The root contains a version and cases. Each case contains `case_id`, `question`,
`required_facts`, `forbidden_claims`, `required_evidence`, and
`allow_insufficient_evidence`. A required fact has a stable `fact_id`, one or
more case-insensitive answer phrases, one or more case-insensitive evidence
content markers, and one or more canonical evidence targets (`source_id`,
`logical_path`, and optionally `chunk_id`). A case may
also define a deterministic answer profile for exercising incomplete,
unsupported, or refusal behavior. Unknown fields, duplicate IDs, empty phrases,
and invalid evidence targets are rejected before any query runs.

## Evaluation semantics

For each query result, the evaluator records the generated answer, validated
citations, trace diagnostics, and final model-context passages. It then computes:

- `fully_correct` when all required facts are present, required evidence is
  cited and supports those facts, no forbidden claim is present, and the
  insufficient-evidence expectation is met;
- `partially_correct` when at least one required fact is present but the full
  authored expectation is not met;
- `incorrect` when the answer is non-empty but required facts are absent or
  insufficient-evidence behavior is wrong;
- `unsupported` when a forbidden/unsupported claim is present or a required
  claim has no matching supporting citation.

The report includes required-fact coverage, citation validity, citation
coverage, citation support precision, forbidden/unsupported claims,
insufficient-evidence success, retrieved/fused chunk IDs, final passage IDs,
retrieval queries, expansion state, and backend/generator identities. Citation
validity remains the existing fail-closed production behavior; this evaluator
only measures quality after validation.

## A/B and reporting

The runner evaluates every case under named configurations with the same corpus,
question, authored expectations, and deterministic generator. The first
baseline configurations are `expand_context=True` and `expand_context=False`.
Configuration identity is retained in every case result and aggregate report.
Results are sorted by case ID then configuration name. Numeric values use fixed
decimal formatting and the checked-in Markdown report is generated from the
same report object used by tests.

## Testing and acceptance

Tests will cover strict case loading, complete/partial/incorrect/unsupported
classification, citation support and coverage, correct and incorrect
insufficient-evidence handling, A/B execution, diagnostic retention, stable
aggregation, and byte-stable report generation. The fixture corpus will include
Binder/SELinux, QNX Resource Manager, TrustZone/PKI, multiple sections, and
distractors. The baseline test command will run entirely offline and will not
alter the production `KnowledgeBase` behavior or persisted state.
